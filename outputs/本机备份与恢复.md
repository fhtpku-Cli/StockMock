# 本机备份与恢复

本说明适用于单个人本机账户。备份保存在本人私有、Git忽略的本机目录，不上传、不云同步，也不新增自动备份服务。数据库、密码和运行配置必须成套保存；单独保存数据库不能保证移动目录后可正常登录和启动。

文档状态复核：2026-11-14。当前0.5.0成套保全及部署验收见[发布记录](0.5.0发布收尾与验收.md)，后续港美股日历维护的独立保全与原库保留见[日历维护记录](2027交易日历核对与更新计划.md)。D1手动工具、结果说明及新的完整隔离恢复已通过独立复核，结果见[D1实施与验收](D1手动备份实施与验收.md)。E1发布已实际用D1完成正式账户成套备份及材料检查，原库原位部署并通过数据保留验证，见[E1记录](E1复盘走查与实施计划.md)第8节；这不等于本轮重新执行正式账户恢复演练。旧版恢复材料继续保留，禁止把发布备份直接覆盖已有新账。

2026-10-24 已完成 0.4.1 隔离恢复演练，实际范围见[本轮集成验证](0.4.1集成验证.md)。演练使用完整受控测试账本、测试密码及独立规则，未覆盖正式账户。真实个人账户的正式恢复只在本人明确需要时进行，不能把这次演练理解为已替换正式数据。

0.4.5升级边界：新程序可以读取旧快照JSON，新增首次失败元数据后，0.4.4的严格字段检查可能无法读取新记录。发布保全用于核对和保留现场，不代表只切回旧代码即可安全回退；尤其不能用升级前数据库覆盖升级后新产生的账本。正式异常时停止已核对归属本项目的服务，保留当前库和现场并向前修复；若另需兼容回退，先验证具体方案。0.4.5已在新私有目录完成正式保全和原库升级，切换时0活动单、当天不完整0、旧10表保持；没有恢复覆盖账户，实际结果见[执行记录](0.4.5执行与验收记录.md)。

## 应保存的完整材料

| 材料 | 用途与注意事项 |
| --- | --- |
| `backend/data/paper.sqlite3` 的一致副本 | 包括所有轮次、现金、订单、幂等请求、流水、快照、公司行动、计划、提示、普通笔记、正式结论、监测状态和动态资格；运行中使用SQLite在线备份 |
| `backend/.local-password` | 保持原访问密码；当前用户所有、普通文件、权限0600，不打印内容 |
| `backend/.runtime.json` | 保存Host、Origin、安全Cookie及人工暂停等原设置；当前用户所有、普通文件、权限0600 |
| 配置中 `STOCKMOCK_INSTRUMENTS_FILE` 指向的文件 | 配置引用外部证券规则时必须一并复制；移动后把绝对路径改为恢复副本中的路径 |
| 对应源码与版本 | 保留已部署版本对应的源文件或源码归档，不能只保留一个未来会更新的工作目录 |
| `backend/pyproject.toml`、`backend/uv.lock`、`frontend/package.json`、`frontend/bun.lock` | 按对应版本恢复Python/Bun依赖；不混用其他版本锁文件 |
| 对应 `frontend/dist` | 保留正式前端包；也可用对应源码和锁文件重新构建。候选测试包必须放独立目录 |

已有数据库时不能把单独复制一个正在写入的SQLite主文件当作完整备份；WAL中可能仍有已提交数据。两种可选方式是运行中调用SQLite在线备份，或正常停服后复制整个数据库目录。后者必须先确认本项目进程已结束，不能只复制主文件并遗漏同目录的WAL/SHM。

## 手动成套备份入口

D1手动入口如下，交付证据以实施记录为准。由维护者执行，不需要本人为每个细小改动运行Terminal。源目录应为已核对的实际部署目录，配套文件均须存在；备份与源码/配置/静态包切换串行。运行中的数据库通过SQLite在线备份读取，包含WAL已提交数据，不停服务，也不初始化或升级原库。

1. 核对部署记录中的源码提交和前端构建来源，准备一份独立保留、来源可靠的前端参考包。当前HEAD可能只更新后端或文档，不能直接当成静态包来源。工具比较实际包与参考包的全部字节、文件集合及对应前端构建输入；参考包历史归属仍由维护者负责核实。找不到可靠参考时，先在隔离目录按对应源码/锁文件构建并核对，不将未经核对的文件当正式包。
2. 准备本人所有、权限0700、非符号链接的私有父目录。项目内只允许Git忽略的 `work/` 子目录；项目外须自行确认不在Git或云同步范围。目标不能位于源静态包或参考包内部，尤其不能把含密码的备份放进网页可访问的 `frontend/dist/`。每次使用全新子目录名称。以下命令中路径和提交是占位，替换后执行；密码和配置正文不进入命令参数：

```sh
cd /项目路径/StockMock
umask 077
mkdir -m 700 work/manual-backups
backend/.venv/bin/python scripts/backup.py create \
  --root /项目路径/StockMock \
  --destination /项目路径/StockMock/work/manual-backups/本次唯一名称 \
  --static-reference /私有路径/已核实前端包 \
  --static-source-commit 完整Git提交
```

父目录只在第一次创建；已存在时检查其归属与0700权限，不重复创建。目标备份目录由工具独占创建，不手动预建，不复用失败目录。

3. 阅读命令结果：成功才生成完整清单，列出时间、位置、配套版本及材料。失败返回非零和安全原因；部分文件留在本次目录，旧成功包保留，不自动覆盖、清理或续写。源码归档最多等待600秒，数据库读取单独限制5秒；不要因看见SQLite副本便把部分包称为成功。
4. 随时可只读检查已有包：

```sh
backend/.venv/bin/python scripts/backup.py inspect \
  --backup /项目路径/StockMock/work/manual-backups/本次唯一名称
```

检查核对完整材料、权限、文件集合/大小、归档及数据库完整性，不修权限、不写回包、不追随原外部规则路径。检查通过只表示材料符合本工具要求，不等于已恢复运行；没有hash，不声称能识别任意同尺寸内容篡改。完整恢复须继续执行下面的隔离演练。

没有周期任务、每日恢复点承诺、自动删除或云同步。手动执行频率决定可恢复数据的新鲜度；同盘副本不保护硬盘损坏。不得将含密码、配置和账本的包上传到公有仓库或公开报告。

## D2候选：备份出错后怎么办

本节适用于已完成白话提示修订的D2候选，尚未合并部署；实际状态见[D2记录](D2备份失败定位实施与验收.md)。你只需看清发生了什么、这份备份能不能用、下一步怎么办，不需要理解错误码。

| 提示表达的情况 | 你需要知道的事与下一步 |
| --- | --- |
| 备份时有文件发生了变化 | 这次备份没有完成。请让维护者检查相关文件，再重新备份；提示本身不能证明是谁或什么程序改了文件 |
| 程序文件或配套文件对不上 | 请让维护者确认程序文件是否配套，处理后再备份，不要自己删除或覆盖文件来绕过检查 |
| 已有同名文件夹 | 本次没有生成新备份。保留原文件夹，给这次备份换一个未使用的名称；这不代表原文件夹里的备份已经检查通过 |
| 保存位置不能使用 | 请让维护者检查文件夹的访问权限，或选择另一个只有你能访问的保存位置 |
| 无法确认旧备份能否恢复 | 先不要用它恢复，保留原件并请维护者核对。这不等于已经确定它损坏了 |
| 无法保存失败说明 | 请保留屏幕上的提示交给维护者。没有说明文件也不代表备份成功 |
| 原因暂时不清楚 | 不要反复重试，也不要删除旧备份；把当前提示交给维护者排查 |
| 命令没填完整或有不认识的选项 | 请让维护者按使用说明检查命令，不需要把密码填进命令里 |

重新备份前先处理问题。保存用的文件夹应已存在且只有你能访问；为本次备份选一个新名称，**不要提前创建这个新名称的文件夹**，工具会自行创建。失败留下的文件和旧备份都保留，不覆盖、不续写、不自动重试。新备份完成后还要检查是否齐全；确认真实恢复可用仍需另行在隔离环境演练，不能覆盖正式账户来试。

供维护者排查：`failure.json`仍保留原`code/context`，其`message`与白话提示一致；这些字段表示失败检查位置，不保证根因已知。保存目录仍须为本人所有且权限0700，具体命令见上方维护步骤；安全检查不因文案简化而取消。记录不写密码、配置正文、私人来源路径或原始异常。不要公开整个私有备份包或未经检查的终端输出。

## 先隔离演练，再决定正式恢复

恢复目录与备份源分开，永远保留源副本。先复制源码、数据库、配套私有文件和锁文件到新的候选目录；不要直接指向正式数据库，也不要把正式端口8000抢给测试进程。按锁文件安装依赖（后端`uv sync --frozen`，前端`bun install --frozen-lockfile`），前端使用独立输出目录构建。依赖目录不可跨系统当作可靠可移植备份。

恢复时必须逐项确认数据库、密码、运行配置及已声明的外部规则均存在，不能因缺配置而接受默认空设置，也不能因为没有数据库而启动出新账户。复制后将 `STOCKMOCK_INSTRUMENTS_FILE` 改为恢复目录中的规则副本；不要让候选继续读取原位置。权限不正确时先修复为本人所有、目录0700和文件0600。密码文件保持原值，不能为了通过检查改成新密码并宣称原登录已经恢复。

用恢复版本的真实`--check-config`检查配置与依赖；0.4.1检查通过只表示配置/依赖有效，未启动服务，不证明行情或后台已工作。随后在隔离端口用真实应用、数据库、认证和两个worker启动；行情必须禁用网络撮合或采用明确受控来源。0.4.1历史演练曾替换端口、时间与外部行情；本轮D1使用系统分配的独立回环端口和明确受控行情，保持真实系统时间，应用及生命周期真实运行。没有让固定8000的正式启动器抢占端口。

实际核对当前及归档轮次、所有表所有字段、精确金额、订单与请求、流水、计划/提示/笔记/结论、快照、公司行动和资格；认证后读取实际API。等待后台自然运行，核对两个worker的时间推进。升级只允许写恢复副本，保留升级前源库和对应旧版本源码，必要时先用旧版本只读解析源库，不能把升级后的副本当作唯一回退材料。

若本人以后确需替换正式账户，先对当前正式账户再做一套完整备份，再用 `backend/.venv/bin/python scripts/service.py stop` 正常停止确认归属本项目的服务。确认已停后才替换已验证的完整数据库目录及配套材料，修正正式路径和权限，然后运行检查并通过`service.py start`启动。启动后重新认证核对原记录、资格与两个后台任务；失败时保持停止状态，依据刚保留的完整副本恢复，不得静默新建账户。本轮没有执行这一步。

## 失败时怎么定位

缺失数据库/配置/密码/规则时先补齐备份，不要继续启动。权限错误按当前用户及0600/0700修正；依赖缺失按同版本锁文件安装。0.4.1的安全日志位于 `backend/data/logs/service.log`，当前日志及最多三份轮转历史有大小上限；日志不可写时检查安全标准错误，不假定错误已经记录。

若Python解释器不存在或操作系统拒绝启动，Python日志本身不能工作。先运行 `backend/.venv/bin/python scripts/service.py status`（解释器可用时）并检查本项目系统任务状态；不要卸载未知同名任务，也不要杀死占用端口的其他进程。Mac整机重启仍由本人决定并继续后置；iPhone基础及Duo已本人通过，不重复要求。候选服务重载不能替代整机恢复验收。
