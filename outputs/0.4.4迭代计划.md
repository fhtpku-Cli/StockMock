## 产品决定

**D1　采用每笔订单首次成功处理的合格观察版本（B08）。** “完整区间”表示经证据支持的五分钟市场时段已经结束，不表示供应商已收齐所有迟到成交、也不保证OHLCV以后不修订。价格以系统当次合法观察为准，不能从之后版本中事后挑选更有利价格。

### D1.1 时间与来源

- CN现端点的标签按北京时间区间结束解释，US现端点按美东区间结束解释；起点为结束减五分钟。必须有同源一分钟OHLCV聚合、开盘/午休/收盘锚点及现场首次出现/变化的共同证据，不能只用标签网格或历史收盘标签。来源研究与实测见`observation-policy/source-semantics/`。没有找到官方完整性契约须如实披露；不能把经验佐证写成供应商保证。若两种对齐解释无法区分或实际数据与解释冲突，停止相关来源的批准并回计划复核，不自行平移时间或换源。
- 解析器仅输出`interval_start = market_time - 5分钟`、五分钟整边界、`market_time <= retrieved_at`、正且有限价格与成交量的样本，保留符号、来源、币种、格式和重复标签等已有检查。CN 15:00跨14:57依旧不可用于成交；US当日收盘末根及提前收盘使用现日历。Futu已有起点转终点语义保持，只观察，不因本次放开港股交易。
- 不再增加固定定稿余量，也不以出现后继作为替代证明。缓存仍保留首次真实取得时间，不能缓存命中时刷新它；不改现端点、60秒缓存、60秒worker周期或日线。
- 撮合入口另验证带时区的`interval_start < market_time <= retrieved_at <= process_now`、固定五分钟形状与正且有限价量，再推进水位或利用截止外样本确认截止。系统时钟回拨或未来取得时间不合格时拒绝处理，不伪造时间。交易时段、生效时间和限价属于订单资格，沿用D2/D3，不与基础行情合法性混淆。
- 同一次来源响应的重复标签继续整批拒绝，不能按数组顺序挑价格。Engine直接收到冲突批次也须在订单循环前拒绝，不推进水位、不部分成交，不借此立即终止订单；真实来源错误仍走D4失败保护。

### D1.2 统一选取和历史不回写

- 规则的单位是“每笔订单”，不是所有页面请求中的全局首次观察：在首次成功提交的撮合事务中，按市场时间升序处理来源相符、水位之后的合格样本；每个区间只处理一次。所有本次已入库的活动单使用同一批输入。一次整体事务回滚不算已经采用该版本。
- 合格区间不满足限价或日价格边界时也消费水位；同标签后来改价不能再试。基础无效样本（如零量、未来时间、错误形状）不消费水位，后续合法响应仍可处理。已消费更晚标签后补到更早区间仍按既有水位语义跳过，不扩大为补洞系统。
- 并发处理A/B两版本时，SQLite既有写事务串行化，第一笔成功提交的处理决定该订单结果；后续事务读取水位/终态后跳过。不承诺网络取得时刻最早者必胜。重启、重复请求、撤单或刷新不能重新选择已处理版本；已结束订单不回填。
- 不同处理时刻的订单允许采用不同观察。现有在途下单可能在取行情前记录`active_at`、网络返回后才入库；若晚于另一次撮合，它按自己首次处理的版本决定。该场景须真实并发测试并诚实说明，不能宣称所有订单共享永久统一的行情版本，也不顺带修改受理生效时刻。
- 停机期间未处理的有效历史区间，使用恢复后实际取得的版本，保留真实取得时间并按D3追加延迟处理说明。未曾保存的旧行情版本不补造。本方案不新增共享历史样本仓库；已有已成交结果和订单水位足以防重撮合。

### D1.3 成交依据与展示

- Order新增默认`None`的`fill_observation`，保存实际用于成交的完整Quote字段：symbol、currency、source、interval_start、market_time、retrieved_at、price、volume、tradable。可用不可变专用模型或现有Quote类型，必须保持Decimal和时间精度，无浮点金额转换。
- 在首次账务变更前构造并验证快照；与订单成交结果、现金、持仓和流水同一SQLite事务保存。单笔DomainError失败单不得留下成交快照或半笔账，其他订单仍按D5推进；未知异常保持整个事务回滚。
- 旧订单默认无快照，不补造取得时间；旧终态价格、流水、事实不回写。升级活动单保留source、active_at、cutoff、last_sample_at和资金占用，只处理尚未消费的区间。旧JSON可读、可归档、可导出；新增可空字段不改变旧业务值。
- 成交卡片简短提示“按当时取得的行情成交，后续修订不改本笔记录”；展开详情和已成交复盘事实显示实际来源、区间、取得时间与采用价格。新增`fill_observation`仅在`order_filled`事实中保留；其他事件的后端事实投影及CSV事实JSON须为空或省略，不能仅靠前端隐藏而给委托提交/撤单申请事件回填未来依据。本轮不顺带重做既有其他Order事实字段。旧成交记录显示“历史记录未保存完整行情依据”，不把空值解释为异常。
- CSV沿用既有完整事实JSON承载新增依据，不新增另一套导出列；实际下载解析核对字段、精确价格及时间。图表说明成交依据可能与后来修订的历史图表不同，不新增专业行情对账功能。

### D1.4 新单、提示、估值与等待体验

- 新单参考价仍取当前分钟行情，并保留20分钟`quote_stale`和无数据保护；下单参考价不是已锁定的成交价。计划到价提示仍只消费新鲜的有效样本，保留既有每版本每条件幂等，不在恢复后补发过时提示。
- 首页/持仓估值使用现有独立报价路径，日线图表也保持原来源职责；不得宣称所有页面、提示和成交共享同一观察版本。
- 去除人为余量后，只要第一个符合订单生效条件的五分钟区间结束且来源已返回，就能进入原缓存/worker流程。例如10:01受理，首个候选通常为10:05–10:10；不再额外固定等17分钟，但仍可能有来源固有延迟、缓存、worker及网络耗时。只报告现场测得的延迟，不承诺实时。
- 新单/提示的20分钟限制不放宽。通过真实响应与真实`Engine.prepare()`证明：旧余量曾人为排除而实际已结束的新鲜区间现在可受理；真正超过20分钟仍拒绝。来源固有延迟若仍导致间歇不可用，如实量测并报告，不能称已消除所有拒单。

**D2　截止边界与截止确认（B09、B12）。** 先定义"候选区间"：可能使订单成交的区间，须完整落在闭区间 `[active_at, cutoff]` 内，即起点 ≥ 生效时间、**结束时刻 ≤ 截止时刻（含等于）**，起点和终点前一刻都处于本应用支持的连续交易时段，并以 5 分钟为边界。

截止边界（B12，用户 2026-10-28 决定）：

- 结束时刻**等于**截止的区间是有效候选区间，照常按价格、日价格边界和市价保护判断是否成交。美股 15:55–16:00 区间（提前收盘日为 12:55–13:00）因此可以成交。
- 只有结束时刻**晚于**截止的样本才直接确认截止，即 `advance()` 中的判断由 `event >= cutoff` 改为 `event > cutoff`。
- 结束时刻等于截止的区间处理完而未成交时，它必然是最后一个候选区间，当场按下面第 2 条确认 `cancelled` 或 `expired`，不再等待下一根样本。
- A 股截止为 14:57，任何 5 分钟边界都不等于它，14:55–15:00 区间仍因跨过 14:57 不可成交，A 股到期行为不变。盘中撤单的截止时刻带秒和微秒，几乎不会恰好落在边界上；若恰好相等，按同一口径视为该区间在撤单生效前已完整走完。
- 设计稿 §4.1 已写"区间完整落在可成交区间中"；§4.3 的旧概括需同步明确："恰好等于截止不成交"只适用于时点报价语义，区间样本以本条闭区间规则为准。本应用撮合只使用区间样本。主协调者只同步 §4.3、§4.4 中被 D2–D4 替代的必要段落，不另定规则。

活动订单在 `now ≥ cutoff` 之后按以下顺序判定：

1. 没有任何候选区间（例如午休中挂出又撤掉）→ 直接确认 `cancelled` 或 `expired`，原因写"截止前没有可成交的完整区间"。
2. 最后一个候选区间已被处理（`last_sample_at ≥ 最后候选区间的结束时刻`）且未成交 → 确认 `cancelled` 或 `expired`，原因写"截止前全部可成交区间已处理，未满足条件"。
3. 超过 `最后候选区间结束时刻 + 20 分钟`（并且不早于 cutoff），最后候选区间仍未到达，且 D4 允许超时 → `terminated`，沿用"数据不足，未确认成交"。
4. 其余情况继续等待，保持占用。

另外两点：

- 现有路径"出现市场时间晚于截止的样本就确认"保留，边界按 B12 由"≥"改为">"。
- 撤单和到期的区分规则不变：`cancel_at ≤ expires_at` 为撤单，否则为过期。

这样一来，盘中撤单通常也能提前约一个区间得到确认。这是同一规则的自然结果，不是新行为面。

**D3　延迟处理仍使用有效区间成交（B10，方案 A）。** 撮合不再要求 `now - event ≤ 20 分钟`。只要区间同源、区间已结束且时间语义有效、晚于下单与生效时间、结束时刻不晚于截止，且 `last_sample_at` 之后尚未处理过，即使处理时间晚于 20 分钟，也照常判断成交。

- 设计依据：设计稿 §4.4 写明"已保存且未处理的有效样本可继续处理"；§4.5 例 3 写明撤单截止之前已满足条件就按成交处理。
- 下单时的 20 分钟时效（`quote_stale`）、估值过期判断和计划到价提示的 20 分钟时效**都不变**：它们回答的是"现在的行情是否新鲜"，不是"历史区间能否作为成交依据"。
- 订单原因要能解释结果：
  - 确认时间晚于成交区间结束 20 分钟以上时，原因追加"后台延迟处理，按市场时间 HH:MM 的完整区间成交"；
  - 订单曾申请撤单、但截止前已有满足条件的区间时，原因写"撤单截止前已有满足条件的完整区间，撤单未生效"（设计稿 §4.3 要求显示撤单未生效的原因）。

**D4　行情请求失败时不凭墙钟时间终止（B10 的配套条件）。** 方案 A 下，电脑刚唤醒时网络往往还没恢复，第一次请求会失败；如果此时直接按 D2-3 终止，会把可以用的数据丢掉。因此：

- Worker 在内存中记录每只证券"连续请求失败的起始时间"。请求成功、服务启动，或两次 tick 间隔超过 5 分钟（视为刚恢复）时，清空记录。
- 只有本轮请求成功，或该证券已连续失败满 20 分钟，才允许 D2-3 超时终止。
- 持续运行中的真实数据故障仍在大约 20 分钟后释放占用，与现行行为一致。
- 实现上 `Engine.process()` 增加关键字参数 `allow_timeout: bool = True`。直接调用的既有测试和其他路径行为不变。

**D5　预留与成交使用同一取整算法，单笔异常隔离（B11）。**

- `accounting` 提供唯一的"成交所需金额"函数（成交额四舍五入到分，加费用四舍五入到分），`fill()` 改用它。
- 买入预留取 `max(现有 ceil 预留, 按价格边界计算的成交所需金额)`。现有预留金额只会持平或增加 0.01，不会减少。
- `process()` 中单笔订单推进时抛出 `DomainError`，只把**该订单**置为 `terminated`，原因写"成交校验未通过（错误码），未成交并释放占用"，记录 `confirmed_at` 和日志，然后继续处理同一证券的其他订单和截止。
- 捕获后继续的前提是订单级原子性：把可能抛 `DomainError` 的日历计算（尤其买入的 `sellable_time()`）及领域校验全部移到首次现金、持仓或流水变更之前；若实现采用订单临时 `State`，则只能在成功后合并。不能只加 SQLite SAVEPOINT 而保留已修改的内存状态。优先选择符合现有代码的最小前置校验方案，不增加通用事务框架。
- 实施时须用真实 SQLite 测试证明：晚期日历失败和资金/持仓校验失败均不留下现金、持仓或流水变化，且该证券其他订单继续推进。现有外层事务、幂等和唯一约束保持。
