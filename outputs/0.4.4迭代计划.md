## 产品决定

**D1　完整区间（B08）。** 一根 5 分钟区间同时满足以下两条，才是"来源已定稿的完整区间"：

1. 标签时刻 ≤ 取得时刻（现有条件）；
2. 同一响应中已经出现更晚的区间，**或者**取得时刻 ≥ 区间结束时刻 + `SETTLE`（定稿余量）。

- `SETTLE` 初值 90 秒，依据是审查采样：新浪对最新区间大约每 13–60 秒刷新一次。Q02 实测后可在复核中调整。如果实测出现"已有后一根区间但前一根仍在变化"，则取消"后一根已出现"这一条，只保留时间余量。
- 规则在解析层统一实现，适用于 A 股、美股和港股（Futu）。港股仍只观察，不因此启用交易。
- 撮合、计划到价观察、证券启用核验和目录导入读取同一批样本，自动受益，不再各自加一层判断。
- 代价：成交和撤单确认平均推迟约 1–1.5 分钟，最坏约 3.5 分钟（余量 + 60 秒行情缓存 + 60 秒 worker 周期）。
- 当日最后一根区间之后不会再出现更晚的区间，只能按时间余量定稿；结合 B12，美股到期订单要等 15:55–16:00 区间定稿后才确认，约在 16:01:30–16:03:30。

**D2　截止边界与截止确认（B09、B12）。** 先定义"候选区间"：可能使订单成交的区间，须完整落在闭区间 `[active_at, cutoff]` 内，即起点 ≥ 生效时间、**结束时刻 ≤ 截止时刻（含等于）**，起点和终点前一刻都处于本应用支持的连续交易时段，并以 5 分钟为边界。

截止边界（B12，用户 2026-10-28 决定）：

- 结束时刻**等于**截止的区间是有效候选区间，照常按价格、日价格边界和市价保护判断是否成交。美股 15:55–16:00 区间（提前收盘日为 12:55–13:00）因此可以成交。
- 只有结束时刻**晚于**截止的样本才直接确认截止，即 `advance()` 中的判断由 `event >= cutoff` 改为 `event > cutoff`。
- 结束时刻等于截止的区间处理完而未成交时，它必然是最后一个候选区间，当场按下面第 2 条确认 `cancelled` 或 `expired`，不再等待下一根样本。
- A 股截止为 14:57，任何 5 分钟边界都不等于它，14:55–15:00 区间仍因跨过 14:57 不可成交，A 股到期行为不变。盘中撤单的截止时刻带秒和微秒，几乎不会恰好落在边界上；若恰好相等，按同一口径视为该区间在撤单生效前已完整走完。
- 设计稿 §4.1 已写"区间完整落在可成交区间中"；§4.3 的旧概括需同步明确："恰好等于截止不成交"只适用于时点报价语义，区间样本以本条闭区间规则为准。本应用撮合只使用区间样本。主协调者只同步 §4.3、§4.4 中被 D2–D4 替代的必要段落，不另定规则。

活动订单在 `now ≥ cutoff` 之后按以下顺序判定：

1. 没有任何候选区间（例如午休中挂出又撤掉）→ 直接确认 `cancelled` 或 `expired`，原因写"截止前没有可成交的完整区间"。
2. 最后一个候选区间已被处理（`last_sample_at ≥ 最后候选区间的结束时刻`）且未成交 → 确认 `cancelled` 或 `expired`，原因写"截止前全部可成交区间已处理，未满足条件"。
3. 超过 `最后候选区间结束时刻 + 20 分钟`（并且不早于 cutoff），最后候选区间仍未到达，且 D4 允许超时 → `terminated`，沿用"数据不足，未确认成交"。
4. 其余情况继续等待，保持占用。

另外两点：

- 现有路径"出现市场时间晚于截止的样本就确认"保留，边界按 B12 由"≥"改为">"。
- 撤单和到期的区分规则不变：`cancel_at ≤ expires_at` 为撤单，否则为过期。

这样一来，盘中撤单通常也能提前约一个区间得到确认。这是同一规则的自然结果，不是新行为面。

**D3　延迟处理仍使用有效区间成交（B10，方案 A）。** 撮合不再要求 `now - event ≤ 20 分钟`。只要区间同源、已定稿、晚于下单与生效时间、结束时刻不晚于截止，且 `last_sample_at` 之后尚未处理过，即使处理时间晚于 20 分钟，也照常判断成交。

- 设计依据：设计稿 §4.4 写明"已保存且未处理的有效样本可继续处理"；§4.5 例 3 写明撤单截止之前已满足条件就按成交处理。
- 下单时的 20 分钟时效（`quote_stale`）、估值过期判断和计划到价提示的 20 分钟时效**都不变**：它们回答的是"现在的行情是否新鲜"，不是"历史区间能否作为成交依据"。
- 订单原因要能解释结果：
  - 确认时间晚于成交区间结束 20 分钟以上时，原因追加"后台延迟处理，按市场时间 HH:MM 的完整区间成交"；
  - 订单曾申请撤单、但截止前已有满足条件的区间时，原因写"撤单截止前已有满足条件的完整区间，撤单未生效"（设计稿 §4.3 要求显示撤单未生效的原因）。

**D4　行情请求失败时不凭墙钟时间终止（B10 的配套条件）。** 方案 A 下，电脑刚唤醒时网络往往还没恢复，第一次请求会失败；如果此时直接按 D2-3 终止，会把可以用的数据丢掉。因此：

- Worker 在内存中记录每只证券"连续请求失败的起始时间"。请求成功、服务启动，或两次 tick 间隔超过 5 分钟（视为刚恢复）时，清空记录。
- 只有本轮请求成功，或该证券已连续失败满 20 分钟，才允许 D2-3 超时终止。
- 持续运行中的真实数据故障仍在大约 20 分钟后释放占用，与现行行为一致。
- 实现上 `Engine.process()` 增加关键字参数 `allow_timeout: bool = True`。直接调用的既有测试和其他路径行为不变。

**D5　预留与成交使用同一取整算法，单笔异常隔离（B11）。**

- `accounting` 提供唯一的"成交所需金额"函数（成交额四舍五入到分，加费用四舍五入到分），`fill()` 改用它。
- 买入预留取 `max(现有 ceil 预留, 按价格边界计算的成交所需金额)`。现有预留金额只会持平或增加 0.01，不会减少。
- `process()` 中单笔订单推进时抛出 `DomainError`，只把**该订单**置为 `terminated`，原因写"成交校验未通过（错误码），未成交并释放占用"，记录 `confirmed_at` 和日志，然后继续处理同一证券的其他订单和截止。
- 捕获后继续的前提是订单级原子性：把可能抛 `DomainError` 的日历计算（尤其买入的 `sellable_time()`）及领域校验全部移到首次现金、持仓或流水变更之前；若实现采用订单临时 `State`，则只能在成功后合并。不能只加 SQLite SAVEPOINT 而保留已修改的内存状态。优先选择符合现有代码的最小前置校验方案，不增加通用事务框架。
- 实施时须用真实 SQLite 测试证明：晚期日历失败和资金/持仓校验失败均不留下现金、持仓或流水变化，且该证券其他订单继续推进。现有外层事务、幂等和唯一约束保持。
