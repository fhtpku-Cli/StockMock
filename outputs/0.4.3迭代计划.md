## 产品决定

业务请求在服务器开始处理时归属于当时的活动轮次。等待外部行情或汇率期间若用户重开练习，该旧请求应提示“练习轮次已变化，请刷新后重新操作”，不能默默使用新轮本金或外币。此核对使用既有轮次主键和最终写事务，不延长事务包围网络请求。已有成功记录的同请求重试优先返回已保存结果，不因后续重开而再次执行或错误拒绝。

订单同请求重试始终给出该订单已知最终状态；归档不应让已成交状态退回受理中。历史数据库不批量改写，不迁移严格轮次 JSON 格式，不改变历史成交与本金。

异常行情内容必须显式失败；来源恢复后可按既有短错误缓存重试。只有通过已有 SDK 结构验证的响应才允许进入 24 小时缓存，继续使用受资源限制的独立解码函数，不执行完整第三方脚本、不增加假行情。

## Q07/Q08 可直接执行的验证步骤

前端使用真实 Chromium 的 OMO `omowright` 驱动，必要时用 WebKit 复核本轮改动涉及的交互。启动入口沿用本轮 `.omo/evidence/audit-20261027/ui/server.py` 的受控应用方式，由前端所有者新建 `.omo/evidence/0.4.3/ui/server.py`，端口 `8135`、SQLite 位于同一私有证据目录；生产 API、认证、SQLite 和 React 真实运行，仅行情来源采用受控数据。候选构建固定输出 `.omo/evidence/0.4.3/candidate-dist`。主协调者使用实际浏览器独立打开候选，记录步骤与截图；不将 API 测试冒称浏览器操作。

1. 桌面 `1280×900` 登录候选，从自选进入标的，正常下单并在委托页读到“已受理”；用受控行情完成成交后，在详情看见成交价与最终状态。预期订单数和数据库一致、资金变化与费用一致。
2. 用候选专属测试控制阻塞一次行情读取，在浏览器提交订单，通过第二已认证客户端重开练习，解除阻塞。真实订单 API 应返回 409，页面显示轮次变化并要求刷新；新轮订单与流水保持空，不能出现受理成功。测试控制只存在私有启动脚本，不进入产品。
3. 同一真实 API 场景核对换汇轮次冲突，浏览器原有换汇窗口显示服务器中文错误。若实际浏览器无法稳定制造网络交错，保留真实 HTTP 并发证据及浏览器错误展示证据，明确各自边界，不伪称浏览器完成了交错动作。
4. `390×844` 打开复盘，输入结论、偏差和下次行动；第二客户端修改覆盖事实，首端保存收到冲突后点击“刷新事实并保留草稿”。三个字段保持，事实覆盖更新；注入一次“服务端成功但响应丢失”的传输失败后重试同提交，结论条数不增加第二条且页面最终成功。
5. 在隔离 32 条复盘主体中加载第一页 25 条、下一页至 32 条，按“已复盘→待复盘→已复盘”切换，逐次与真实 API 的完整计数及主体集合对照。检查浏览器没有未处理异常，不重跑与本版无关的日期全站截图。
