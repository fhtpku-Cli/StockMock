macOS WebKit 设置 iPhone UA、触控、DPR 3 后仍没有出现原图中的空白高日期框；桌面 WebKit 日期显示当前日期占位符。这表明桌面引擎的移动设备仿真不能证明覆盖 iPhone 原生日期渲染。正式 8000 和候选 8427 服务返回相同 CSS 文件名、字节数及筛选规则，暂未发现部署包分歧。

## 根因状态与最小修正方向

已排除：在所测桌面引擎中，单纯 951px 宽触控、iPhone UA、DPR 3、字体放大、连续 resize 都不会导致日期外框重叠；本轮正式/候选公开 CSS 无分歧。

仍属假设：iOS 原生 `appearance:auto` 日期控件存在电脑 WebKit 未模拟的最小尺寸或空值绘制行为，可能越过 CSS 指定尺寸。现有其他日期组件已禁用原生外观，可作为最小兼容修正候选：仅给 `.record-filters input[type="date"]` 同样的 `appearance:none` 与日期值左对齐，保留原生日期语义、48px 高度、可读文字及 min/max。不把候选方向写成已证实根因，也不在未获集中修复通知前编辑产品。

缺失的决定性证据是原失败 iPhone 环境的 input/label 边界与外观开关前后对照。若后续只能交付兼容候选，必须明确“电脑回归通过，原设备修复待确认”，不能称 B03 已复现并修复。截图不是克隆目标，不应为了匹配错误外观而修改正常页面。

## 引擎机制补充与受控对照

[WebKit 官方固定版本源码](https://github.com/WebKit/WebKit/blob/d18d3ce1ba1a3a241c0842080a7fbfcd9f8942fd/Source/WebCore/rendering/ios/RenderThemeIOS.mm#L455-L487) 的 iOS 日期样式路径会在非固定像素宽度下设置最小宽度并把盒模型改为 `ContentBox`。本组件使用 `width:100%`，符合该路径的前提；源码快照保存在 `.omo/evidence/0.4.2/frontend/RenderThemeIOS.mm`。这提供了兼容性修改的具体依据，但该源码版本不等于用户设备实际安装版本。

执行 `node work/0.4.2/frontend/repro-box-model.mjs`，仅在独立 WebKit 页内临时切换日期盒模型，产品源码保持原样。正常日期为 187.109×48px；改为 `content-box` 后变成 213.109×70px、越过父 label 26px，与相邻输入重叠，市场标签随底部对齐下移；恢复 `border-box` 后回到 187.109×48px。现象与原图一致，唯一明显差别是电脑引擎仍显示日期占位符。

证据为 `.omo/evidence/0.4.2/frontend/box-model/measurements.json` 和 `normal.png`、`reconstructed-ios-content-box.png`、`restored-border-box.png`。这是基于官方引擎机制的受控重建，不是 iPhone 实机复现，也不是 `appearance:none` 修正已经通过原设备验收。最终仍应表述为：原图确认缺陷、桌面原生场景未复现，兼容修正电脑回归后等待 Duo 原设备复验。
